# 单篇论文专项

叠加在 SKILL.md 的通用流程之上，不替代它。综述走 @references/survey.md。

## 论文元信息标注

页面 header 区域必须标注论文的**发表时间**和**发表 venue**：

- **发表时间**：至少精确到年月（如 `2026.05`）
- **发表 venue**：发表在顶会/顶刊（NeurIPS、ICML、ICLR、ACL、EMNLP、AAAI、CVPR、TPAMI、Nature、Science 等）的，明确标注年份+会议/期刊名（如 `NeurIPS'23`、`ICML'25`）。仅挂 arXiv 未正式发表的标注 `arXiv preprint`
- **被引论文同理**：在深度卡片或引用论文的折叠态中标注 venue 和年份，帮读者快速判断权威性和时效性

## 训练与评测数据（强制）

每篇单篇论文页都要有一个**默认展开**的「训练与评测数据」区域。数据决定结果能否与同方向论文比较，它属于实验结论的必要上下文，不能藏在折叠卡片里，也不能只写一句「在多个 benchmark 上评测」。

先从原文整理所有真正参与本文训练、选型和结论的数据：

- **训练数据**：本文实际用来更新参数的数据集、版本、子集、过滤规则和规模。SFT、RL、蒸馏、偏好优化等阶段分别列行；基础模型原始预训练语料只有在本文继续使用或它直接影响论证时才列。
- **验证 / 选型数据**：用于调超参、early stopping、选择 checkpoint、选择 prompt / policy / 方法变体的数据。说明验证分数只是选型，还是样本、错误、轨迹也回流进训练。
- **测试 / 最终评测数据**：支撑页面结论的每个 benchmark、年份 / 版本和 split。`data-dataset-role="test"` 表示它在跨论文表格中承担最终评测角色；页面显示仍保留作者的原名，例如「Held-out validation（本文最终评测）」而不是擅自改名。
- **评测协议**：样本 / 题目数、metric、每题 generation 数、pass@k / majority vote、decoding 设置和 checkpoint 选择规则，只记录原文确实报告的内容。
- **污染与重叠**：论文讨论去重、数据污染、train–test overlap 或同源数据时，紧跟数据表说明；未讨论就不替作者推断。

页面使用稳定字段，方便读者横向比较：

| 角色 | 数据集 / 版本 / split | 规模与子集 | 在流程中做什么 | 更新 / 选型边界 | metric / 生成协议 |
|---|---|---|---|---|---|
| Train | `<name>` | `<N / subset / filter>` | `<SFT / RL / distill…>` | `<更新哪些参数>` | `—` |
| Validation | `<name or 未使用>` | `<N>` | `<调参 / 选 checkpoint>` | `<什么信息回流>` | `<selection metric>` |
| Test | `<benchmark + year/version + split>` | `<N>` | `<最终评测>` | `<是否用于选 checkpoint；是否独立>` | `<metric + K + decoding>` |

HTML 外层加 `data-data-interface`，每个角色行加稳定标记：

```html
<section data-data-interface>
  <table>
    <tbody>
      <tr data-dataset-role="train">…</tr>
      <tr data-dataset-role="validation">…</tr>
      <tr data-dataset-role="test">…</tr>
    </tbody>
  </table>
</section>
```

缺失信息也要占位：

- 论文没有训练过程：Train 写「不适用：本文不更新模型参数」。
- 没有独立验证集：Validation 写「未使用独立验证集」，并说明 checkpoint 如何确定。
- 原文没给规模、过滤或 decoding：对应格写「论文未披露」，不要留空，也不要根据常识补数字。
- 一个角色有多个数据集：每个数据集单独一行；benchmark 很多时可按同一套评测协议分组，但名称、版本和 split 不能省略。

完成标准：读者只看这个区域，就能回答「模型用什么数据学、用什么数据选、最终在哪些数据上报分，以及评测信息有没有回流」。

## 叙事主线

```text
这篇论文要解决什么问题
→ 已有方案怎么做的、卡在哪
→ 本文的做法（核心贡献）
→ 有意思的细节
→ 实验结论一句话
```

按这条线组织 section，具体展开如下。

### 1. 问题定义（轻量）

用 1–2 段白话说清「为什么需要这篇论文」，不堆术语。如果问题本身抽象，画一张最小示意图让读者秒懂。**论文开头就给了 motivating example（一个具体的输入输出或场景）的，优先用它**——让读者一看就知道在说什么。

### 2. 已有方案速览（Related Work 可视化）

- **不要照搬 related work 的引用列表**，只挑真正承担「起点、直接对照、被本文补足」作用的 1–3 种方案。顺带引用的论文只保留一句定位和原文链接，不递归展开。
- 每种关键方案用一张**可展开的卡片**呈现。卡片是选择性阅读，不是主线正文的替代品。
- **折叠态属于主线，必须显示**：方案名称 + venue/年份 + 它在当前论证中的角色 + 与主线直接相关的做法 + 它留下的具体缺口。禁止只写该论文的通用摘要。
- **展开态属于可选细节**：pipeline / 架构图、输入 → 处理 → 输出、2–3 段方法说明、具体例子和局限性。展开内容只能解释折叠态已经提出的论点，**不能引出新的页面主线**。
- 如果读者必须展开卡片才能理解本文动机或方法，说明渐进式披露失败：把必要结论提炼回折叠态或相邻正文。
- 所有卡片折叠时，这一部分原则上控制在一屏内；卡片之后用一段连续正文明确收束共同缺口，自然引出本文方法。

目的是让读者在进入本文方法前，已经对「别人怎么做」有画面感，从而理解本文方案的动机。

### 3. 本文方法（重头戏，花最多篇幅）

- **pipeline / 架构图是全文最重要的图，必须有。** 取图和说明格式见 @references/ingest.md。
- **伪代码可视化**：论文给了 Algorithm 伪代码的，可以用带语法高亮的代码块展示，也可以把关键步骤拆成可交互的分步流程图（点击切换步骤 + 高亮当前行）。
- **具体示例**：论文在方法部分给了 running example、输入输出样例、分步骤实例的，**必须保留**。用高亮块、表格或分步卡片呈现，让读者跟着例子走一遍方法流程。图片型示例（模型输出截图、可视化结果）直接嵌入并配说明。
- 复杂方法可以拆成「总览 → 各模块细讲」的渐进结构，但**每一步都要回答「为什么这么做」**。

### 4. 有意思的点（可选，方法之后）

论文中值得单独拿出来说的内容——巧妙的 trick、反直觉的发现、设计取舍的讨论、与其他工作的有趣联系——用独立小节呈现。

### 5. 实验结论（轻量）

**不要逐表逐图搬运数字。** 用 1–2 句话概括「在哪些 benchmark 上比谁强多少」，或者用一张 metric card 呈现最核心的数字即可。

先放上面的「训练与评测数据」区域，再展示结果。数据表是在界定证据，和搬运大段实验数字不是一回事。

- 论文自己提到了 limitations / failure cases 且说得有道理的，也值得一两句话带出来——这往往比数字更能帮读者判断这个方法适不适合自己的场景
- 论文给了**定性示例**（生成结果对比图、case study、可视化对比）的，挑最能说明方法优劣的 1–2 个嵌入，比干巴巴的数字更直观

读者来这里是快速 view 方法，不是审稿。

## 跨 section 原则：保留具体示例

论文中的具体示例（input-output 样例、case study、running example、反例、failure case 截图），**不管是图还是文本，只要有助于理解，都要保留并嵌入对应位置**。示例是读者从「好像懂了」到「真的懂了」的桥梁。

**但呈现方式要克制**：

- 超过 5 行的具体示例（代码片段、交互日志、input-output 对比）包裹在默认折叠的 `<details><summary>` 中，折叠态用一行总结说明示例展示了什么
- 5 行以内的短示例可直接展开显示
- 大段代码/日志不应直接撑开页面打断阅读节奏。**保留 ≠ 平铺**

## 关键对照论文必须配图 + 方法讲解

只有被选为 Related Work **关键对照卡片**的论文 / 系统必须有原论文的图 + 清晰的方法讲解；顺带引用不需要为了满足格式而强行扩写。

关键对照至少要讲清楚：

- **它要解决什么问题**（动机，一两句话）
- **它的核心做法是什么**（输入什么 → 怎么处理 → 输出什么）
- **与本文主线的关系**（它在当前叙事中扮演什么角色）

判断标准：读者没读过这篇关键对照论文，看完卡片展开内容后应该能向别人转述它的核心方法；但折叠卡片后，主线仍必须完整。前者保证细节深度，后者保证叙事连续性。

**Pipeline / 架构图要求**：关键对照方案和本文方法的核心方案必须配 pipeline 或架构图。优先从原论文获取，找不到原图时自制 CSS / SVG。但方案本身不以 pipeline 为核心（纯数学推导）时不必强凑；核心价值体现在**接口/交互设计**上（新 API、新交互模式）时，代码示例 + before/after 对比比示意图更直观。

## 篇幅分配原则

根据论文在叙事中的角色分配篇幅，**不要每篇论文都给相同的展开深度**：

| 角色 | 配置 |
|---|---|
| **引子/过渡**（证明某个可能性、为后续工作铺路） | 1 张核心架构图 + 1–2 段方法概述 + 局限性一句话。快速过渡，不恋战 |
| **转折点**（引入新范式、改变方向） | 1–2 张图 + 3–4 段方法 + 具体示例 + metric card。读者需要在这里建立对新范式的理解 |
| **终点/重点**（当前最先进、主要推荐） | 2–3 张图 + 完整方法讲解 + 具体示例 + 详细 metrics。花最多篇幅 |

判断标准：这篇论文在整个叙事弧线中扮演什么角色？如果它只是「证明了一种可能性」然后被后续工作超越，就不要花跟终点论文一样的篇幅。

> **注意**：上表的 metric card 和具体数字只适用于**单篇论文精读页面**。综述语境下读者关心的是方法本身，不是精确的 benchmark 数字——三个层级都改成一句话定性描述有效性即可（「显著优于 baseline」「证明了 X 的可行性」「在 Y 场景下有效但 Z 场景有局限」）。
