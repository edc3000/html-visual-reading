# 取材

四种输入形态，做法各不相同。先判断拿到的是哪一种，再选对应做法——不要不分场景地一律「读一遍全文再说」。

## URL

抓正文，不是抓整张网页的所有 DOM。优先 Read，其次 WebFetch。

arXiv 论文**不要抓 PDF 页或摘要页**，用 HTML 版本：

```
https://arxiv.org/html/<id>v<ver>/
```

抓到之后先判断这是单篇论文还是综述——标题含 survey / review / overview / tutorial，或正文结构以分类梳理多篇工作为主、没有提出自己的新方法，就是综述，走 @references/survey.md；否则走 @references/paper.md。

## 本地文件

- **md / txt / 源码**：直接读。
- **pdf**：不要自己解析，用 pdf skill 提取文本和结构。

## 本地文件夹（代码仓库 / 工程项目）

**先摸结构，再读细节。不做全文通读。** 目标是能一句话复述「这个项目在干什么」，而不是记住每一行实现。

摸结构的顺序：

1. **README** —— 项目自己怎么介绍自己
2. **目录树** —— 模块怎么划分，哪些是核心、哪些是辅助
3. **入口文件** —— 程序从哪里开始跑（`main.*`、`index.*`、`cli.*`、`SKILL.md` 之类）
4. **配置文件** —— 依赖了什么、怎么跑起来（`package.json`、`pyproject.toml`、`Makefile` 之类）
5. **tests / examples** —— 现成的 running example 素材在这里

摸完这五层再决定要不要往下深挖某个具体模块——只挖主线里真正需要讲清楚的那部分，不是挖到底。完整流程见 @references/project.md。

## 对话内容

用户要求把「当前这轮对话已经聊出来的结论」做成可视化页面时，**直接使用对话里已经产出的结论，不要重新检索或重新分析**。这一步的输入就是对话本身。

# 图片规范

**最高优先级：让读者看懂。** 图片存在的唯一理由是帮读者理解，所有规则都服务这个目标。

## 取图来源与优先级

1. **原材料的图优先**。作者精心画的 pipeline / 架构图，准确性和信息密度远超自制图，可信度也更高。**动手画任何图之前，先尝试拿原图。**
2. 本地资源目录 / md 文件里引用的图片 / 网页正文里的 `<img>`
3. 自制 CSS / SVG 示意图，仅在下面两种情况：
   - 原文确实没有对应的图，且所有取图途径都不可用
   - 有原图，但在教学页正文宽度下无法清晰阅读（见「主图可读性」）

**适用边界**：自制 SVG/CSS 图适合展示流程、架构、数据流等空间关系；但如果核心创新是**接口设计**或**交互模式变化**，用代码块 + before/after 对比比示意图更直观——不要强行把一切都画成图。

## arXiv 取图

图片 URL 格式为 `https://arxiv.org/html/<paper_id>v<version>/<filename>.png`。获取方式：用 `curl` 或 WebFetch 拉 `https://arxiv.org/html/<paper_id>v<version>/` 的 HTML 源码，从 `<img src="...">` 提取相对路径（通常形如 `x1.png`、`figures/xxx.png`），拼接为完整 URL。

**必须验证**：

```bash
curl -sI "<图片 URL>"
```

确认返回 `HTTP 200` 且 `content-type` 是 `image/*`，确认能加载再嵌入 HTML。校验不过的图不要往页面里塞。

**⚠️ 不要用 ar5iv**：`ar5iv.labs.arxiv.org` 是第三方 LaTeX→HTML 渲染服务，**不对外暴露图片静态文件**——请求其图片路径会 redirect 到论文摘要页，导致 `<img>` 全部 404。

**回退路径**：arXiv HTML 版不可用时（部分旧论文未生成 HTML），检查论文的 GitHub 仓库 `img/` 或 `figures/` 目录。Related work 引用的其他论文同理——去对应论文的 arXiv HTML 页面拿图。

## 本地文件夹取图

按这个清单逐个扫，不止 `assets`：

```
assets/  images/  img/  figures/  docs/  static/  .github/
```

README 和文档里 `![](...)` 引用的图也算，把相对路径解析出来。

**本地图片必须 base64 内联**（页面要单文件自包含）。内联前先看体积：

```bash
sips -g pixelWidth -g pixelHeight <图>   # 看尺寸
```

- 宽度超过 1600px 的先等比缩到 1600px：`sips --resampleWidth 1600 <图> --out <新图>`
- 体积超过 300KB 且不含 alpha 的转 JPEG：`sips -s format jpeg -s formatOptions 80 <图> --out <新图>`。**这一步有损**——带小字标注的架构图压完可能糊掉，这种图宁可保持原样或改用 SVG
- **SVG 不要走 sips**，它是矢量格式，直接读文件内容内联即可（注意 `sips -g pixelWidth` 对 SVG 会返回一个假的数字，别被骗了）
- 全部图片内联后总体积超过 5MB 时，回头砍图

内联命令：

```bash
python3 -c "import base64,sys;p=sys.argv[1];print('data:image/png;base64,'+base64.b64encode(open(p,'rb').read()).decode())" <图>
```

MIME 按真实格式写，**不要按扩展名猜**——`.png` 结尾的文件里装着 SVG 内容是常见的事，写错 MIME 浏览器会静默显示空白。

## mermaid / graphviz / PlantUML 源码不算「现成的图」

README、设计文档里常常嵌一段 mermaid 代码块画流程图。这种源码**不能直接渲染进产物**：渲染需要外部 JS 库，走 CDN 违反零外部请求，把库整份内嵌又体积不可接受。

正确处理：

1. **优先转译成分步流程图或静态 SVG。** 源码里的节点和连线是现成的结构，照着译即可——这比自己凭空设计一套流程更忠于原意，也比放弃不用更省信息。
2. **不要把源码原样贴成代码块。** 读者要看的是图表达的结构，不是这段源码——贴源码等于把渲染的活丢给读者脑内完成。

转译不算「找到现成图直接用」，也不算凭空自制——在契约和 section 规划里如实标注「转译自 README 的 mermaid」。

## 收图标准

**收**：架构图、Pipeline 图、机制流程图、能一眼说明核心创新点的示意图。

**不收**：

- 实验结果的柱状图 / 折线图（用 metric card 数字替代）
- prompt 模板截图（用文字描述替代）
- ablation（消融实验）图表
- 纯数据对比表格的截图

这类图对读者没有解释力，塞进去只是凑数。

## 数量克制

每个主题 / 每篇论文最多嵌入 **1–2 张图**，重点论文可放宽到 3 张。**只有在找不到合适的现成图时才自己画 SVG，不为凑图而凑图。** 有些主题就是没有一张图能讲清楚，那就不放图，用文字和例子讲。

## 主图可读性（强制）

方法主图是读者理解全文最关键的视觉锚点，**可读性优先于「必须用原图」**：

- 在桌面正文宽度下，关键模块名、箭头含义和阶段顺序必须无需放大即可读清
- 若原图信息过密、字号过小、缩放后糊，或 CSS `max-height` 会把宽图压扁，则：
  1. 用忠实于原文数据流的清晰 SVG / CSS 图作为**默认主图**
  2. 把原图放到「查看原图 ▸」折叠区，供核对
- 禁止为了塞进原图而牺牲主线可读性；也禁止自制图偏离原文真实依赖
- 主图不要设置过小的 `max-height`；宽流程图优先完整显示，必要时允许横向滚动，**不要压扁**

## 图片说明格式

**每张嵌入的图都必须配可展开的中文说明卡片**（无例外）。此规则**仅适用于图片**；代码块、交互示例等非图片内容见下方。

图片本身信息密度高但读者未必看得懂——说明卡片是从「看到图」到「理解图」的桥梁。实现方式：图片下方放一个可点击展开的说明区域（`展开说明 ▸` / `收起 ▴`），采用渐进式结构：

- **折叠态（默认可见）**：紧跟图片的一行 caption，一句话概括这张图整体在讲什么——读者扫一眼就知道图的主题。
- **展开态（点击深入）**：
  - 按图中的**关键模块 / 阶段 / 节点逐个分点说明**，每点包含：这个模块是什么、做了什么、为什么这么设计、与其他模块的数据流关系
  - 图中有箭头/连线的，说明每条连线代表什么数据或控制流
  - 图中有颜色/分区的，说明每个区域的含义
  - **最低深度**：至少 3–5 个分点（简单图除外），每点 1–2 句话。复杂架构图应逐节点/逐阶段展开
  - 结尾可加一句「一句话总结」收束

> 判断标准：一个没读过原文的同学，看完图和展开说明后，能向别人转述这个方法的完整流程吗？如果不能，说明不够。

**非图片内容的折叠格式**：代码示例、接口定义、交互日志等改用 `<details><summary>`，`<summary>` 写一句话总结说明内容展示了什么，不需要图片说明式的 3–5 点分点展开。
