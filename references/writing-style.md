# 中文行文规范

这份文档决定读者读到的东西好不好懂。图做得再对，文字写不好，「递进式阅读」就只是排版好看的碎片堆砌。

**关于例子**：这个 skill 的输入形态很杂——论文、综述、开源项目、API 文档、技术博客都可能。下面的例子刻意分散在不同领域，别把某个领域的具体说法当模板照抄，要抓的是每条规则背后的判断。

读者画像见 SKILL.md；section 标题怎么写、要不要写总结章见 @references/contracts.md；折叠态摘要的格式要求见 @references/visual-patterns.md。

---

## 每条规则都有过头的方向（先读这条）

下面每条规则都在纠正一种常见毛病。但**任何一条用力过猛，都会变成另一种毛病**，而且往往比原来的更难看——原来的毛病只是平庸，过头的毛病是做作。

| 规则 | 不足 | 过头 |
|---|---|---|
| 标题写成问题 | 干巴巴的名词短语 | 抖机灵、戏剧腔、拟人化 |
| 讲透为什么 | 只写操作步骤 | 每句话都论证一遍，读者被绕晕 |
| 解释术语 | 把读者卡在材料自造的概念上 | 连 `rollout` 都要立一张卡 |
| 数字给参照系 | 甩一个裸数字 | 每个数字都配类比，页面变成科普读物 |
| 配类比 | 抽象得没法想象 | 比喻堆成串，喧宾夺主 |
| 并列改列表 | 大段文字墙 | 满页都是列表，没有一段连贯叙述 |
| 折叠态带摘要 | 只挂一个标题 | 摘要写得比正文还长，折叠失去意义 |

**自检方法**：写完通读一遍，哪一处让你自己觉得「这里是不是有点用力」，那就是用力了，改回朴素的写法。读者要的是把事情讲明白，不是欣赏作者的文笔。

## 讲透为什么，不只讲是什么

这是整份文档里最容易被忽略、却最决定页面价值的一条。

「它做了什么」是说明书，读者看完只能复述；「它为什么这么做、为什么不那么做」才是 know-how，读者看完能迁移到自己的场景。**页面的价值全在后者。**

每个关键设计至少要回答其中一个：

- **为什么是这个选择**，而不是那个显而易见的替代方案
- **取舍换来了什么**：放弃了什么，得到了什么
- **什么情况下会失效**——失效边界往往比成功案例信息量更大
- **这个数字/阈值是怎么定的**

**正例**（数据处理）：把同一位置的多次测量合成一个值时，不停在「取中位数」这个操作上，而是接着说明为什么——「同一个位置可能被反复测到，其中夹着尖峰噪声；中位数比均值更不容易被极端值拉偏。」读者由此学到的不是「这里要用中位数」，而是「有极端值污染时中位数比均值稳」，换个领域照样用得上。

**反例**：「对信号按 0.5 单位分箱做中位数聚合。」读者知道了操作步骤，不知道为什么不用均值、不知道箱宽为什么是 0.5，换个场景就复现不出来。

## 解释密度：解释材料自造的，不解释行业通用的

**不是每个术语都要解释。** 判断标准只有一条：目标读者读到这里会不会卡住。默认读者是熟悉 LLM 的后训练工程师，所以两个方向都会翻车：

- **行业通用词一个都不要解释**：rollout、SFT、reward、context window、tool calling、harness、train/val/test split、agent loop、过拟合、幂等。给这类词摆一张概念卡，等于当面告诉读者「我觉得你连这个都不懂」，比不解释更伤人。
- **材料自造的说法、非标准缩写、含义重叠的概念，必须解释**。这是页面真正的活。
- **最危险的一类：在材料里有特殊含义的常见词**。某篇论文里的「expert」特指模型里的一组参数、某个项目里的「session」特指一份磁盘上的状态目录——读者会按自己的经验读过去，然后越读越不对，而且不会意识到是哪里出的岔。这类词必须在第一次出现时点破：「这里的 X 不是通常意义上的 X，指的是……」

**密度也要控。** 一页里需要正式摆上概念卡的术语，通常就是术语契约里那 3–8 个骨干概念。其余的在行文里带一句话说清就行，读者的视线不必为此停下来。如果你发现自己列了十几张概念卡，先回头问：这些词真的每个都拦路吗，还是我在把词汇表当内容写。

**正例**（该解释，且解释到位）：「论文说的 context artifacts 不是模型这一轮看到的内容，而是外部存着、按需调进来的材料——所以『没进 context』有两种完全不同的原因：窗口装不下，或者压根没被检索到。」

**反例（漏解释）**：「Learner 每轮从 buffer 采样并更新 policy。」如果这篇论文里的 buffer 有特殊的淘汰规则、policy 指的是 prompt 而不是权重，这句话每个词读者都认识，但整句理解全错。

**反例（解释过头）**：给 `rollout` 立一张概念卡——「rollout：让模型把任务完整跑一遍」。目标读者每天都在用这个词，这张卡除了占位置、拖慢节奏、显得居高临下之外没有任何作用，还会把真正该被看见的那两三个硬骨头概念淹没。

## 不为通俗压掉概念层次

材料区分的几个概念，即使都要通俗化，也不能合并成同一个说法——合并了读者会理解错原文真正在说的结构。

**正例**（论文里三个相邻概念）：原文区分 `context`（模型这一轮实际看到的内容）、`context window`（最多能看多少）、`context artifacts`（外部存着、按需调进来的材料）。译文把三者分别落成「当前上下文」「上下文上限」「外部材料库」，各自给一句定义，并说明三者的包含关系。

**反例**：把三个词统统写成「上下文」。读者看到「上下文不够用」时无法判断是窗口装不下、还是材料压根没被取进来——而原文的整个论证正是建立在这个区分上。

同类陷阱：把「训练集/验证集/测试集」压成「数据」、把「进程/线程/协程」压成「任务」、把「延迟/抖动」压成「慢」。

## 翻译要说人话，宁可留英文也不生造中文

输入经常是英文——论文、README、技术博客。翻译腔是这类页面最容易染上的毛病，而且作者本人往往察觉不到。

**检验方法只有一个：这句话你会对着同事说出口吗。** 说不出口，就是机翻。

三种最常见的翻译腔：

- **英文名词堆砌硬译成中文复合词**。`experiment lineage ledger` 译成「实验血缘台账」——六个字里四个字要单独琢磨，比英文原文还难懂。正确做法是保留英文原名，用一句人话说清它干什么：「每次实验是从哪个版本改来的、改了什么，全都记在一张表里。」
- **填充词泛滥**：「基于……的」「进行……」「实现了对……的处理」「具有……的特性」。中文里这些大多可以直接删掉，句子反而更清楚。
- **被动语态直译**：「该参数被设置为」「结果被证明是有效的」。中文习惯说「把这个参数设成」「结果确实有用」。

**术语处理原则：宁可保留英文原名，也不发明一个没人用过的中文译名。** 读者见到 `rollout` 可以去查、可以对上原文；见到你新造的「推演展开流程」则两头不着——既查不到，也对不上原文。行业里已经通用的译法（训练、推理、过拟合、缓存击穿）照常用，那不叫生造。

**反例**：「本文提出了基于轨迹展开的经验回放机制，该机制通过对模型执行序列的完整记录实现了对失败路径的有效定位。」（每个字都是中文，没有一句是人话，读完不知道它到底在干什么）

## 数字必须给参照系

裸数字对没有该场景经验的读者没有意义，关键数字后面要跟一句「这相当于什么」。

**正例**（性能）：「P99 延迟从 800ms 降到 120ms——用户点下按钮之后，从『明显要等一下』变成『基本没感觉』。」

**正例**（规模）：「训练集 500 万行。按一行一秒的速度人工过一遍，不吃不喝要两个月。」

**正例**（阈值的实际后果）：不甩一个孤零零的「上限 40」，而是接一句——「就算两条轨迹差出 100，也先截到 40：普通情况最多挪动 17，分歧大的最多挪动 4.25。」数字被放进了「最终会改动多少」这个能想象的后果里。

**反例**：「单次修正上限设为 4.50。」数字扔在那儿，读者不知道这算大改还是微调。

**源材料明确拒绝给出具体数字时，参照系改用定性表述，绝不替它编一个。** 有些原文会刻意强调「这个值因场景而异，不能假设固定值」。这时「给参照系」和「不要发明信息」会撞在一起，处理原则是：宁可参照系模糊，也不能给读者一个原文里根本不存在的数字。

**正例**：「大多数平台把每天能提交的次数卡在一个很小的数字（常见的是个位数），具体多少由主办方规则决定。」

**反例**：「每天最多能交 5 次。」（原文根本没说 5 是通用值，甚至明确反对假设固定配额，这里等于编了一个读者会当真的数字）

## 并列要点改列表，关键词加粗

段落里堆超过 3 个并列要点，改成列表；连续 4 行以上没有加粗、没有分点的纯文字，读者的眼睛找不到抓手，要拆。

**正例**（把一段局限拆开，每条用加粗短语开头）：

> - **本地验证偏乐观**：模拟出来的测试样本和真实隐藏样本仍有分布差异，本地误差不能直接当成最终表现。
> - **近邻不一定可靠**：距离近不代表性质一致，边界情况会让参考样本产生偏差。
> - **信号存在重复**：相似的模式可能出现在多个位置，光靠匹配仍可能认错。

读者扫一眼加粗短语就知道每条在说什么，不用逐字读完整句。

**反例**：把这三条压成一段——「本地验证偏乐观是因为模拟样本与真实样本存在分布差异，同时近邻也不一定可靠，因为距离近不代表性质一致，另外信号还存在重复的问题……」读者读到第三条时已经忘了第一条。

## 折叠收起后主线仍要完整（优先级最高）

把页面里**所有折叠区全部收起**，正文从头读到尾必须仍然讲得通、论证链条不断。折叠卡片是给读者补充深度的加餐，不是拿来当承重墙用的——真正支撑结论的关键论证，不能只存在于点开之后。

**正例**：六个步骤卡全部收起后主线依然完整，因为最关键的那句话写在页头不会被折叠的核心结论区里。读者一张卡都不点，也已经知道整个方案在做什么；六张卡只是逐步展开「这一步具体怎么算」「为什么这么设计」。

**反例**：把这句话只写进「步骤一」的折叠卡里，正文和结论区都不提。读者没点开那张卡，读完全文都不知道核心思路是什么。

这条规则的优先级高于其它所有规则：出现冲突时（比如为了不让正文太长而想把关键内容折起来），先保证主线完整，篇幅问题用「删减非必要内容」解决，不用「藏进折叠区」解决。

## 工作语言不下页面，格言句限量

最容易让页面「一眼 AI」的两个毛病，都和材料无关，来自你自己：

**过程词汇泄漏。** 「契约」「主线」「读者画像」「承重墙」「渐进披露」是这套 skill 的工作语言，读者没读过这套 skill。真实翻车案例：把一个项目的 SKILL.md 在架构图里标成「Skill 契约与参考规则」——原材料从头到尾没这么叫过。页面上的每个名词，要么来自材料本身，要么是读者的行业通用词，没有第三个来源。

**格言句式成排。** 这份文档和 SKILL.md 用大量「A 是 X，不是 Y」「先 A，再 B」的对仗句教学——那是写给你的工作语言，不是页面文风的样板。判断句是重音：一页里所有标题都是格言，等于没有重音，读者只觉得被连续说教。同理，本文档里的措辞（「换来了什么、放弃了什么」）是给你的提问框架，不能原样抄成页面标题。

**自检**：写完把全部 h2/h3 抽出来连读一遍。像目录，过；像语录合集，改——同一句式（「A 不等于 B」「先 A 再 B」「把 A 变成 B」）从出现第二次起逐个改成带具体名词的平实短语。

## 禁用词

以下词一律不用：`TL;DR`、`太长不看`、`综上所述`、`笔者认为`、`众所周知`、`不言而喻`。要么是英文缩写读者未必认识，要么是「我说了算」式的空洞收尾，对理解没有帮助。@references/verify.md 的静态检查会逐字扫这几个词。

**正例**：核心结论直接分行给三句话——要解决什么、怎么解决、最后结果如何，不需要任何套话收尾。

**反例**：「综上所述，笔者认为这个方案的优势众所周知，不言而喻。」
