# 写 HTML 前的五份契约

在设计 section 或组件之前，先完成下面五项。它们是你和用户之间的工作文档：指导全文，但不出现在页面上。「契约」「主线」「读者画像」是本 skill 的过程词汇，页面文案里不用（原材料本身在用这个词的除外）——页面上的每个名词，要么来自材料，要么是读者的行业通用词。

**契约写完停下来交给用户确认，得到明确同意再进入写页面阶段。** 不要自行判断「应该没问题」就直接往下写——契约错了，整页都得重写。

---

## 1. 读者契约

写明目标读者已经知道什么、还不知道什么。默认采用 SKILL.md 里的「LLM 后训练工程师」画像，避免两种极端：

- 把 rollout、harness 等常用工程术语全部翻译成冗长白话
- 默认读者理解材料自创术语，直接堆缩写和公式

模板：

```text
读者已经知道：<列出来，这些词直接用，不解释>
读者不知道：<列出来，这些是页面要负责讲清的>
```

**项目场景的读者契约**通常是：读者是同水平的工程师，但从没见过这个项目——他懂 CLI、懂 git、懂 pytest，但不知道这个项目里 `converge`、`evidence level`、`graveyard` 分别指什么，也不知道这几个模块谁调用谁。

---

## 2. 术语契约

提取承担核心推理作用的 3–8 个术语，逐个确定：

| 原文术语 | 页面采用的表述 | 一句话定义 | 与相邻概念的区别 | 第一次出现在 |
|---|---|---|---|---|

同一个原文术语不得在页面中随意切换成多个中文说法。原文区分多个层次时，**禁止为了省事把它们合并**。例如 `context function`、`context artifacts`、`context` 不能全部写成「上下文」。

当概念容易被理解成已有工程概念时，主动说明关系和边界：

```text
A 是否属于 B？
A 是 B 的完整实现，还是其中一个子系统？
A 比 B 多了什么、少了什么？
实验 / 代码中 A 的接口具体被限制成什么？
```

**项目场景**：项目自造的角色名、状态名、阶段名（`pending` / `converged` / `parked`）、目录约定，都要进术语契约。项目里被赋予特殊含义的常见词最危险——`task`、`session`、`run`、`checkpoint` 在每个项目里含义都不同，读者会按自己的经验误读。

### 术语使用原则

- 常见 LLM 工程术语可以直接使用，不要为「白话」而制造更模糊的新说法
- 材料专属术语第一次出现时，保留英文并给一句精确定义；后文保持一致
- **如果术语名称本身不帮助理解，先描述机制，再在括号中给名称**
- 公式只在帮助理解关系时保留；如果公式只是给简单规则贴标签，正文先讲规则

```text
不佳：论文使用 (1+1)-ES 搜索。

更好：每轮只生成一个候选，与当前最佳版本比较并保留胜者；
论文将这种选择方式称为 (1+1)-ES。
```

## 3. 数据流契约

对训练、搜索、进化、反馈循环类方法，先写清：

- 每个阶段读取什么
- 每个阶段修改什么
- 每个阶段输出什么
- train / validation / test 分别承担什么职责
- 验证集只提供最终分数，还是其样本、轨迹或错误也进入下一轮
- 被比较、替换和保留的对象究竟是什么

禁止只写「验证集选择更好的方案」这种缺少对象和更新边界的表述。至少要说明：

```text
训练反馈如何产生候选
→ 候选何时冻结
→ 验证集如何评分
→ 候选与谁比较
→ 胜者的哪些组成部分进入下一轮
```

**项目场景的数据流契约**换成「一次完整运行的控制流与状态流」：

```text
用户敲了什么命令 / 触发了什么入口
→ 程序读了哪些文件（配置、状态、输入数据）
→ 中间状态写在哪（内存？磁盘？某个 json？）
→ 哪些模块按什么顺序被调用
→ 产物落在哪，长什么样
→ 下一次运行会读到上一次的什么残留
```

最后一条最容易漏，也最能体现一个项目的设计：**有状态的项目里，「上一次运行留下了什么」往往就是它的核心机制**。

## 4. Running Example 契约

方法抽象时，选择一个贯穿方法部分的具体例子。优先级：

1. 材料原文中的 motivating example / running example / case study
2. 与目标读者接近的场景：coding agent、reward model、evaluation harness、tool-use agent、数据生成与过滤
3. 其他无需读者额外学习领域知识的最小例子

例子必须展示实际对象，而不是只换一套抽象名词：

```text
具体输入
→ 系统读取的文件 / 状态 / 数据
→ 中间对象实际长什么样
→ 执行了什么操作
→ 最终输出实际长什么样
```

**不要随意引入法律、医学、金融等需要额外背景的类比**；除非它就是原始任务，而且该例子对理解方法不可替代。

**项目场景**：running example 就是**一次真实的端到端调用**。从用户敲下的那行命令开始，到最终产物为止，中间每个文件的实际内容都要给出片段（超过 5 行的用折叠容器装）。项目文档里的示例、README 里的 quickstart、tests 里的 fixture，都是现成的 running example 素材——优先用它们，不要自己编一个。

---

## 5. 主线契约（最高优先级）

在设计 section 前，必须先把全文压缩成**一个核心问题**：

```text
这份材料究竟要回答什么问题？
```

页面中默认展开的内容必须共同回答这个问题。每个 section 只能承担以下职责之一：

1. 提出核心问题，以及它为什么重要
2. 解释已有方案为什么没有解决好
3. 展示材料给出的关键答案
4. 用证据判断这个答案是否成立
5. 说明答案的适用边界

如果一个默认展开的 section 不能归入以上任一项，删除它，或降为可展开的补充细节。**完整覆盖原文不是目标，最小充分解释才是目标。**

当后文的图片、Related Work、示例数量或格式要求与主线冲突时，优先级始终是：

```text
核心问题与连续叙事 > 必要证据 > 可选细节 > 组件和视觉形式
```

可展开内容只能加深主线已经提出的论点，**不能开启另一条平行叙事**。任何理解核心方法所必需的信息，都必须出现在默认展开的正文或卡片折叠态中，不能藏在点击之后。

### 三条硬规则

1. **section 数量、顺序、命名由材料本身决定，不套固定模板。** 不是每份材料都天然分成「是什么 / 为什么 / 怎么做」三段，该几节就几节。

2. **每个 section 必须能回答「它如何服务那个核心问题」。** 答不上来就删掉，或者降级成正文里的一个可展开细节，不要为了「看起来完整」硬留一节。

3. **最后一节不许是总结章。** 「读完这些，我能拿走什么」「总结与展望」「关键收获」这类 section 一律不排。读者刚读完，不需要有人把说过的话再复述一遍；页头的核心结论已经把「一句话说清楚」这件事做过了。如果结尾确实还有话说，那必是一条前文没安放过的**新判断**（比如「这套做法什么时候别用」），标题就直接写那个判断。

### section 标题自检

「问题背景」「架构设计」的病不在名词短语，而在**任何文章都套得上**。好标题带着这份材料专属的名词——模块名、文件名、阶段名、数字——读者扫一遍目录就知道每节在讲这份材料的哪件事。名词短语只要够具体，完全可以当标题，不必硬改成句子。

| 太泛（哪篇材料都能用） | 好（只有这份材料能用） | 过头（表演腔 / 自造抽象词） |
|---|---|---|
| 问题背景 | 这套系统最初要解决什么问题 | 这套系统当年到底踩了什么坑才被逼出来 |
| 架构设计 | 一个请求进来会经过哪些环节 | 一个请求进来之后，都经过了谁 |
| 数据存储 | state.json：只记机器可验证的事实 | 先创建事实容器，再去填事实 |
| 实验结果 | 比原来的做法好多少 | 它到底赢在哪，赢得漂不漂亮 |
| 错误处理 | 出错的时候会怎么样 | 天塌下来的时候谁来顶 |
| 失败记录 | 失败的方向怎么处理 | 失败方向为什么要办场葬礼 |

两条规则：

1. **标题里的名词必须来自材料或行业通用词。** 材料里没有「事实容器」「过程纪律」这样的词，标题里就不能有——想不出具体说法时，回材料里找那个文件名、那个模块名、那个数字。
2. **判断句标题是重音，限量。** 「A 不等于 B」「先 A 再 B」「把 A 变成 B」这类句式一页至多两三个，同一句式不出现第二次；其余标题用平实短语。写完把全部 h2/h3 抽出来连读一遍——应该像目录，不像语录合集。

判断标准仍然是：**读者会觉得你在陈述，还是觉得你在表演。**
