# 工程项目专项

输入是一个本地文件夹（代码仓库、工程项目、skill 目录、脚手架）时走这条。叠加在 SKILL.md 的通用流程之上，不替代它。

取材顺序（README → 目录树 → 入口 → 配置 → tests/examples）见 @references/ingest.md。

## 这条路最容易翻的车

**页面退化成目录树导览**：一节讲一个目录，每个文件配一段「这个文件负责 xxx」。这是文件清单，不是解读——读者读完知道有哪些文件，仍然不知道这个项目在解决什么问题、为什么这么切分。

判断方法：把你的 section 标题列出来，如果它们和目录名一一对应，就是退化了。**section 由「读者的疑问」决定，不由目录结构决定。**

同样要避免的：把 README 换个说法复述一遍。README 已经存在，读者可以自己看。页面的价值在于 README 没写的那部分——**为什么这么设计、当初是什么问题逼出了这个结构、什么情况下会失效**。

## 项目元信息标注

页面 header 区域标注（能拿到的都标）：

- **仓库地址**（链回去，见 SKILL.md 的源链接硬约束）
- **技术栈 / 语言**
- **规模**：多少个文件、多少行——给读者一个「这是个小工具还是大系统」的量级感
- **最后更新时间**：`git log -1 --format=%cd` 拿；不是 git 仓库就跳过

```bash
git log -1 --format='%cd' --date=short 2>/dev/null
find . -name '.git' -prune -o -type f -print | wc -l
```

## 叙事主线

```text
这个项目要解决什么问题
→ 不用它的时候人们怎么做、卡在哪
→ 它的核心设计：模块怎么切、一次运行怎么走
→ 跟着一个真实例子从头走一遍
→ 关键设计取舍：为什么是这样而不是那样
→ 边界：什么时候别用它
```

### 1. 它要解决什么问题（轻量）

用 1–2 段说清「为什么需要这个项目」。素材通常在 README 开头、`docs/motivation.md`、或者最早那几条 commit message 里。

README 只写了「这是一个 X 工具」而没写为什么的，去代码里找：**大量的防御性检查、重试逻辑、校验步骤，每一处都是某个真实问题留下的疤**。那些才是动机。

### 2. 不用它的时候人们怎么做（对应论文的 Related Work）

这一节不是必须的，但有它页面价值高很多。内容是：手工做法 / 现成替代方案是什么，卡在哪，这个项目补上了什么缺口。

素材来源：README 的对比章节、`docs/` 里的设计文档、issue 里的讨论、代码注释里的「we can't use X because...」。**找不到就不写**，不要自己编一个稻草人对手。

### 3. 核心设计（重头戏）

两张图撑起这一节，缺一不可：

- **模块图**：有哪些模块、谁依赖谁。README 里有 mermaid 架构图的转译过来（见 @references/ingest.md）；没有就照着 import 关系自制 SVG
- **一次运行的流程图**：从入口到产物，控制流怎么走。这张图对应契约里的数据流契约，是全页最重要的图

模块讲解按**角色**分配篇幅，不要每个目录都平均分：

| 角色 | 配置 |
|---|---|
| **核心机制**（这个项目的立身之本） | 完整讲：输入 → 处理 → 输出、关键设计选择、为什么不用显而易见的替代方案 |
| **支撑模块**（核心依赖它，但本身不新颖） | 1–2 段说清它提供什么能力、接口长什么样 |
| **周边**（配置、日志、CLI 解析、脚手架） | 一句话带过，或者干脆不提 |

判断标准：**删掉这个模块，项目还成立吗？** 不成立的是核心，成立的是周边。

### 4. 跟着一个真实例子走一遍（必做）

这是项目类页面和 API 文档最大的区别。选一个真实的端到端调用，从用户敲下的那行命令开始，到最终产物为止，中间每一步的实际内容都给出来：

```text
$ 用户敲的命令
→ 读了哪些文件（给出实际路径）
→ 中间状态写成了什么（给出实际片段）
→ 哪些模块按什么顺序被调用
→ 产物长什么样（给出实际片段）
```

素材优先级：**README 的 quickstart > tests 里的 fixture > examples/ 目录 > 自己造一个**。前三种是项目自己给的真实数据，比自己编的可信得多。

超过 5 行的文件内容片段用 `<details><summary>` 折叠，`<summary>` 写一句话说明这段展示了什么。

### 5. 关键设计取舍（页面价值最高的一节）

这一节回答「为什么这么做」，是读者唯一能迁移到自己项目里的东西。每条取舍写成：

```text
面临的选择 → 项目选了哪个 → 放弃了什么 → 什么情况下这个选择会变成错的
```

**素材在哪里找**（README 里通常没有）：

- **代码注释里的 why**：`# 这里必须用 X，因为 Y 在 Z 情况下会……` 这类注释是纯 know-how，优先级最高
- **测试用例的名字**：`test_does_not_retry_on_4xx` 直接告诉你一条设计决策，以及它曾经被违反过
- **防御性代码**：每个 `assert`、每次输入校验、每个 fallback 分支，背后都有一次踩坑
- **CHANGELOG / commit message**：`fix:` 开头的记录是问题清单，`refactor:` 说明结构为什么变成现在这样
- **docs/ 下的设计文档**：有就是金矿，直接用

**找不到 why 的时候不要编。** 宁可写「代码里选择了 X，文档没有说明原因」，也不要替作者编一个听起来合理的理由——读者会当真。

### 6. 边界：什么时候别用（可选，但通常值得写）

项目的适用范围、已知局限、明确不支持的场景。素材：README 的 limitations、issue 里 `wontfix` 的讨论、代码里明确 raise 的不支持分支。

这一节是唯一可以放在末尾的「结论式」章节——因为它是**新判断**，不是复述前文（见 @references/contracts.md 的硬规则 3）。

## 代码片段的呈现

- **贴代码要克制**。读者不是来 review 代码的，是来理解设计的。一段代码只有在「文字说不清楚」时才贴
- 超过 5 行的折叠，`<summary>` 一句话说明这段在干什么
- 贴之前先问：这段代码删掉，改用两句话描述，读者会不会理解得更快？会的话就别贴
- 贴的时候标注来源路径和行号（`src/runner.py:88-104`），读者能对回原仓库
- **不要贴样板代码**：import 块、`__init__` 里的赋值、CLI 参数定义。它们占篇幅但不承载信息

## 项目里的图

- README / `docs/` 里的 mermaid、graphviz 源码**转译**成 SVG 或分步流程图，不要贴源码（见 @references/ingest.md）
- 本地图片必须 base64 内联
- 项目通常没有现成的架构图，这时自制 SVG 是正常路径，不算「为凑图而凑图」——模块图和运行流程图是这类页面的刚需

## 不是 git 仓库、或者材料极少的项目

- 拿不到 commit 历史时，know-how 只能从注释和代码结构里挖，元信息里的「最后更新时间」跳过不写
- 项目太小（几百行、单文件）时不要硬撑成六节。压成三节：**要解决什么问题 / 怎么做的 / 关键取舍**，配一张流程图，够了。**页面长度应该匹配材料的信息量，撑长了只会稀释**
